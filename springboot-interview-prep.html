Spring Framework Architecture

Core
Core Container

Layered Module Architecture

Spring is built on a modular architecture. The Core Container provides IOC/DI. Built on top are: AOP, Data Access, Web MVC, Test.

  • spring-core: Fundamental abstractions, IOC
  • spring-beans: BeanFactory, bean definitions
  • spring-context: ApplicationContext, events
  • spring-expression: SpEL language support
Spring Boot

What Spring Boot Adds

Spring Boot is an opinionated wrapper around Spring Framework. It adds:

  • Auto-configuration based on classpath
  • Embedded server (Tomcat/Jetty/Undertow)
  • Starter POMs for dependency management
  • Actuator for metrics & health endpoints
  • Externalized configuration support

What's the difference between BeanFactory and ApplicationContext? ▼
BeanFactory is the basic container providing DI. ApplicationContext extends it and adds enterprise features: event publishing, i18n, AOP auto-proxy, web support. In production always use ApplicationContext (specifically AnnotationConfigApplicationContext or Spring Boot's SpringApplication). BeanFactory lazily instantiates beans; ApplicationContext eagerly instantiates singletons at startup.

Spring Boot Internal Working

1. main() → SpringApplication.run()
Entry point. SpringApplication creates an instance, detects web app type (SERVLET, REACTIVE, NONE).
2. Spring Environment Prepared
Loads application.properties/yaml, system env, command-line args. Fires ApplicationEnvironmentPreparedEvent.
3. ApplicationContext Created
AnnotationConfigServletWebServerApplicationContext created. Fires ApplicationContextInitializedEvent.
4. Bean Definitions Loaded
Classpath scanning, @Bean methods, imports processed. All bean definitions registered in BeanDefinitionRegistry.
5. Auto-Configuration Applied
spring.factories / AutoConfiguration.imports processed. Conditional annotations evaluated.
6. Beans Instantiated & Wired
Singletons instantiated. DI performed. BeanPostProcessors run. @PostConstruct executed.
7. Embedded Server Started
Tomcat/Jetty started. DispatcherServlet registered. ApplicationStartedEvent fired.
8. ApplicationRunners Executed
CommandLineRunner and ApplicationRunner beans execute. ApplicationReadyEvent fired.

@SpringBootApplication
public class MyApp {

        app.addListeners(new ApplicationStartupListener());

    }
}

@Component

Auto Configuration Deep Dive

Mechanism

How @EnableAutoConfiguration Works

Spring Boot scans META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (Boot 3.x). Each entry is a config class annotated with @AutoConfiguration.

Conditional

@Conditional Annotations

  • @ConditionalOnClass — if class on classpath
  • @ConditionalOnMissingBean — if no bean defined
  • @ConditionalOnProperty — if property set
  • @ConditionalOnWebApplication — if web app
  • @ConditionalOnBean — if specific bean exists
javaCustom Auto Configuration
@AutoConfiguration
@ConditionalOnClass(DataSource.class)
@ConditionalOnMissingBean(DataSource.class)
@EnableConfigurationProperties(DataSourceProperties.class)
public class MyDataSourceAutoConfig {

    @Bean
    @ConditionalOnProperty(name = "app.datasource.url")
    public DataSource dataSource(DataSourceProperties props) {
        return props.initializeDataSourceBuilder().build();
    }
}
💡
Run ./mvnw spring-boot:run --debug or set debug=true in application.properties to see the Auto-Configuration Report — which configs applied and why.
How do you exclude an auto-configuration?▼
Use @SpringBootApplication(exclude = {DataSourceAutoConfiguration.class}) or in properties: spring.autoconfigure.exclude=org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration
What changed from spring.factories to AutoConfiguration.imports in Boot 3.x?▼
Boot 3.x introduced META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports as the new standard. The old spring.factories still works but is deprecated. The new file is more explicit and improves startup performance because it doesn't need to load all entries at once.

IOC Container Internals

Internals

BeanDefinition Registry

Every bean is described by a BeanDefinition object: class name, scope, constructor args, property values, init/destroy method names. Registered via BeanDefinitionRegistry.

Resolution

Bean Resolution Order

  • Exact type match
  • By qualifier (@Qualifier)
  • By primary (@Primary)
  • By name (field/param name matches bean name)
  • Throws NoUniqueBeanDefinitionException if ambiguous
javaProgrammatic Bean Registration
@SpringBootApplication
public class App {
    public static void main(String[] args) {
        var context = new AnnotationConfigApplicationContext();
        context.registerBean("myService", MyService.class,
            () -> new MyService("custom-config"));
        context.refresh();
        MyService svc = context.getBean(MyService.class);
    }
}
How does @Qualifier vs @Primary work when multiple beans of same type exist?▼
@Primary marks one bean as the default when multiple candidates exist — used at the bean definition site. @Qualifier("name") is used at the injection site to specify which exact bean you want. @Qualifier takes precedence over @Primary.

Lazy Initialization

Default

Eager vs Lazy

By default Spring Boot eagerly creates all singleton beans at startup. With @Lazy or spring.main.lazy-initialization=true, beans are created on first use.

  • Eager: catches wiring errors at startup
  • Lazy: faster startup, useful in dev/test
  • Lazy: errors surface at runtime — risky in prod
Usage

When to Use Lazy

  • Rarely-used heavyweight services (PDF generators, report builders)
  • Dev/test environments for fast startup
  • Serverless functions where cold start matters
  • Avoid globally in production microservices

Circular Dependency

Problem

What is Circular Dependency?

A → B → A: Service A needs Service B, and Service B needs Service A. Spring Boot 3.x throws BeanCurrentlyInCreationException by default (constructor injection).

Solutions

How to Resolve

  • Refactor — extract common logic to a third service (best)
  • @Lazy on one param — breaks the cycle with proxy
  • Setter injection — Spring resolves setter after construction
  • ApplicationContext — manual late lookup
🚨
Circular dependencies usually indicate a design smell — consider whether the classes have single responsibility. Fix the design rather than working around it with @Lazy.

REST API Best Practices

Design

REST Principles

  • Use nouns for resources: /users, /orders/{id}
  • Use HTTP verbs correctly: GET/POST/PUT/PATCH/DELETE
  • Return proper HTTP status codes
  • Consistent JSON response structure
  • API versioning from day one
  • HATEOAS for discoverable APIs (when appropriate)
Status Codes

Correct HTTP Status Usage

  • 200 OK — GET, PUT success
  • 201 Created — POST success, include Location header
  • 204 No Content — DELETE success
  • 400 Bad Request — validation failure
  • 401 Unauthorized — not authenticated
  • 403 Forbidden — not authorized
  • 404 Not Found — resource missing
  • 409 Conflict — duplicate/version conflict
  • 500 Internal Server Error — unexpected
javaREST Controller — Best Practice
@RestController
@RequestMapping("/api/v1/orders")
@RequiredArgsConstructor
public class OrderController {
    private final OrderService orderService;

    @GetMapping("/{id}")
    public ResponseEntity<OrderResponse> getOrder(@PathVariable UUID id) {
        return ResponseEntity.ok(orderService.findById(id));
    }

    @PostMapping
    public ResponseEntity<OrderResponse> createOrder(
            @Valid @RequestBody CreateOrderRequest request) {
        OrderResponse created = orderService.create(request);
        return ResponseEntity
            .created(URI.create("/api/v1/orders/" + created.id()))
            .body(created);
    }

    @PatchMapping("/{id}/status")
    public ResponseEntity<OrderResponse> updateStatus(
            @PathVariable UUID id,
            @Valid @RequestBody UpdateStatusRequest request) {
        return ResponseEntity.ok(orderService.updateStatus(id, request));
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deleteOrder(@PathVariable UUID id) {
        orderService.delete(id);
        return ResponseEntity.noContent().build();
    }
}

Global Exception Handling

java@RestControllerAdvice — Complete Pattern
@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex) {
        return ResponseEntity.status(404).body(ErrorResponse.of(ex.getMessage()));
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ValidationErrorResponse> handleValidation(
            MethodArgumentNotValidException ex) {
        Map<String, String> errors = ex.getBindingResult().getFieldErrors().stream()
            .collect(Collectors.toMap(
                FieldError::getField,
                fe -> Objects.requireNonNullElse(fe.getDefaultMessage(), "Invalid")));
        return ResponseEntity.badRequest().body(new ValidationErrorResponse(errors));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleGeneral(Exception ex) {
        log.error("Unhandled exception", ex);
        return ResponseEntity.internalServerError()
            .body(ErrorResponse.of("An internal error occurred"));
    }
}

public record ErrorResponse(String message, Instant timestamp, String traceId) {
    public static ErrorResponse of(String msg) {
        return new ErrorResponse(msg, Instant.now(), MDC.get("traceId"));
    }
}

DTO vs Entity

Entity

JPA Entity

Represents the database table. Contains JPA annotations. Never expose directly in API — sensitive fields, bidirectional relations can cause infinite serialization loops.

DTO

Data Transfer Object

Tailored view for API consumers. Decouples API contract from DB schema. Use Java Records for immutable DTOs in Java 16+.

javaEntity + DTO + MapStruct Mapper
// Entity
@Entity
@Table(name = "users")
public class User {
    @Id @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;
    private String email;
    private String passwordHash; // NEVER expose in DTO
    @OneToMany(mappedBy = "user", fetch = FetchType.LAZY)
    private List<Order> orders;
}

// Request DTO (record)
public record CreateUserRequest(
    @Email @NotBlank String email,
    @NotBlank @Size(min = 8) String password
) {}

// Response DTO
public record UserResponse(UUID id, String email, Instant createdAt) {}

// MapStruct mapper (generates impl at compile time)
@Mapper(componentModel = "spring")
public interface UserMapper {
    UserResponse toResponse(User user);
    User toEntity(CreateUserRequest request);
}

Validation & Custom Validators

javaCustom Constraint Annotation
// 1. Define annotation
@Documented
@Constraint(validatedBy = PhoneNumberValidator.class)
@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidPhone {
    String message() default "Invalid phone number";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

// 2. Implement validator
public class PhoneNumberValidator implements ConstraintValidator<ValidPhone, String> {
    private static final Pattern PHONE_PATTERN =
        Pattern.compile("^\\+?[1-9]\\d{9,14}$");

    @Override
    public boolean isValid(String value, ConstraintValidatorContext ctx) {
        if (value == null) return true; // use @NotNull separately
        return PHONE_PATTERN.matcher(value).matches();
    }
}

// 3. Use it
public record ContactRequest(
    @NotBlank String name,
    @ValidPhone String phone,
    @Email String email
) {}

Logging Strategy

Levels

Log Level Guidelines

  • ERROR — exceptions, critical failures (alert needed)
  • WARN — degraded but operational (fallback used)
  • INFO — business events, startup, key operations
  • DEBUG — developer diagnostics (dev/staging only)
  • TRACE — fine-grained, method entry/exit (never prod)
Rules

Production Logging Rules

  • Never log passwords, tokens, PII
  • Use structured JSON logging in production
  • Include correlation/trace ID in every log
  • Use parameterized messages: log.info("{}", val)
  • Log at service boundaries (entry/exit)
  • Async logging (LMAX Disruptor in Logback)

Correlation IDs & Traceability

javaRequest Tracing Filter
@Component
@Order(1)
public class CorrelationIdFilter extends OncePerRequestFilter {
    private static final String TRACE_HEADER = "X-Trace-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String traceId = Optional.ofNullable(req.getHeader(TRACE_HEADER))
            .orElseGet(() -> UUID.randomUUID().toString());
        MDC.put("traceId", traceId);
        res.setHeader(TRACE_HEADER, traceId);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.clear(); // crucial — thread pool reuse
        }
    }
}

Dirty Checking

Mechanism

How Dirty Checking Works

On loading, Hibernate stores a snapshot of each managed entity. On session flush, it compares current state with snapshot. If different, it generates an UPDATE SQL automatically.

Performance

Dirty Checking Overhead

With thousands of entities in session, snapshot comparison is expensive. Solutions:

  • Load only what you need (projections)
  • @DynamicUpdate — updates only changed columns
  • Use @Transactional(readOnly=true) for reads — disables dirty checking
  • Keep sessions short
💡
Always annotate read-only service methods with @Transactional(readOnly = true). This disables dirty checking, optimizes connection handling, and signals read replicas for routing.

    User user = userRepository.findById(id).orElseThrow();
    return mapper.toDetailResponse(user); // safe within transaction
}

N+1 Query Problem

Problem

What is N+1?

Loading N parent entities, then issuing N separate queries for each parent's lazy collection. 1 query for users + N queries for each user's orders = N+1 total queries.

Solutions

Fixes

  • JOIN FETCH in JPQL
  • @EntityGraph for selective fetching
  • @BatchSize(size=25) — batch sub-selects
  • @Fetch(FetchMode.SUBSELECT)
  • DTO projections with flat joins
  • Hibernate statistics to detect
💡
Enable Hibernate stats in dev: spring.jpa.properties.hibernate.generate_statistics=true. Check for "query count" in logs. Use p6spy or datasource-proxy to log every SQL with stack trace.

Transaction Management

java@Transactional — Production Patterns
@Service
public class TransferService {

    // Full transaction — any exception rolls back
    @Transactional
    public void transfer(UUID fromId, UUID toId, BigDecimal amount) {
        Account from = accountRepo.findByIdForUpdate(fromId); // SELECT FOR UPDATE
        Account to = accountRepo.findByIdForUpdate(toId);
        from.debit(amount);
        to.credit(amount);
        auditService.record(fromId, toId, amount); // same transaction
    }

    // Read-only - no dirty check, read replica routing
    @Transactional(readOnly = true)
    public AccountBalance getBalance(UUID id) {
        return accountRepo.findBalanceById(id);
    }

    // New transaction for audit — always commits independently
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void recordAudit(AuditEvent event) {
        auditRepo.save(event);
    }

    // Rollback on checked exceptions too
    @Transactional(rollbackFor = BusinessException.class)
    public void process(Request req) throws BusinessException { ... }
}
🚨
Self-invocation trap: Calling a @Transactional method from within the same class bypasses the AOP proxy — the transaction won't start. Always inject the service from outside, or use ApplicationContext.getBean().

Optimistic

@Version — Optimistic Locking

No DB lock. Add a version column. On update, checks if version matches. Throws OptimisticLockException on conflict. Best for low-contention scenarios.

java
@Entity
public class Product {
    @Version
    private Long version;
    private int stock;
}
Pessimistic

SELECT FOR UPDATE — Pessimistic Locking

Acquires DB lock immediately. Other transactions wait. Use for high-contention: inventory, wallet deductions.

java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM Product p WHERE p.id = :id")

JWT Authentication

javaJWT Filter + Security Config
@Component
public class JwtAuthFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req,
            HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String authHeader = req.getHeader("Authorization");
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            chain.doFilter(req, res); return;
        }
        String token = authHeader.substring(7);
        String username = jwtService.extractUsername(token);
        if (username != null && SecurityContextHolder.getContext().getAuthentication() == null) {
            UserDetails userDetails = userDetailsService.loadUserByUsername(username);
            if (jwtService.isTokenValid(token, userDetails)) {
                var authToken = new UsernamePasswordAuthenticationToken(
                    userDetails, null, userDetails.getAuthorities());
                authToken.setDetails(new WebAuthenticationDetailsSource().buildDetails(req));
                SecurityContextHolder.getContext().setAuthentication(authToken);
            }
        }
        chain.doFilter(req, res);
    }
}

@Configuration
@EnableMethodSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        return http
            .csrf(AbstractHttpConfigurer::disable)
            .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/v1/auth/**", "/actuator/health").permitAll()
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }
}

AOP in Spring Boot

javaCustom Logging AOP Aspect
@Aspect
@Component
@Slf4j
public class PerformanceLoggingAspect {

    @Around("@annotation(LogExecutionTime)")
    public Object logTime(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();
            long duration = System.currentTimeMillis() - start;
            log.info("{}#{} took {}ms",
                pjp.getSignature().getDeclaringTypeName(),
                pjp.getSignature().getName(), duration);
            return result;
        } catch (Throwable ex) {
            log.error("Exception in {}", pjp.getSignature(), ex);
            throw ex;
        }
    }

    // Pointcut: all public methods in service layer
    @Pointcut("execution(public * com.example..service.*.*(..))")
    public void serviceLayer() {}

    @Before("serviceLayer()")
    public void logServiceEntry(JoinPoint jp) {
        log.debug("Entering: {}", jp.getSignature().getName());
    }
}
Why doesn't @Transactional work when called within the same class?▼
Spring AOP creates a proxy around your bean. When you call a method internally (this.method()), you bypass the proxy and the AOP advice (including transaction management) is never invoked. To fix: inject the bean into itself via @Autowired @Lazy, or use AspectJ weaving for self-invocation, or restructure to avoid the pattern.

Custom Annotations

java@RateLimit custom annotation with AOP
// Annotation definition
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RateLimit {
    int requests() default 100;
    int perSeconds() default 60;
}

// AOP handler
@Aspect
@Component
public class RateLimitAspect {
    private final Map<String, RateLimiter> limiters = new ConcurrentHashMap<>();

    @Around("@annotation(rateLimit)")
    public Object enforce(ProceedingJoinPoint pjp, RateLimit rateLimit) throws Throwable {
        String key = pjp.getSignature().toShortString();
        RateLimiter limiter = limiters.computeIfAbsent(key,
            k -> RateLimiter.create((double) rateLimit.requests() / rateLimit.perSeconds()));
        if (!limiter.tryAcquire()) {
            throw new TooManyRequestsException("Rate limit exceeded");
        }
        return pjp.proceed();
    }
}

            throw new BadRequestException("Unsupported type");
    }

Production Best Practices

✅ Use constructor injection — enables immutable, testable services
✅ Always validate input at the controller layer with @Valid
✅ Never expose entities directly — always use DTOs in API responses
✅ Use @Transactional(readOnly=true) for all read-only operations
✅ Structured JSON logging with correlation IDs in every log line
✅ Define pool sizes explicitly — never rely on defaults for Hikari/Redis/threads
✅ Externalize all secrets — never commit to source code

Common Production Issues

Issue

Connection Pool Exhaustion

Symptoms: Requests hang, timeout waiting for DB connection.

Causes: Long transactions, connection leaks, pool too small.

Fix: Enable leak-detection-threshold, check for missing @Transactional, tune pool size.

Issue

OOM / Memory Leak

Causes: Static collection holding references, ThreadLocal not cleared, Metaspace growth from dynamic class loading.

Fix: Heap dump analysis (Eclipse MAT), -Xss, -Xmx tuning, always clear MDC in finally blocks.

Issue

N+1 in Production

Detect: Enable hibernate.generate_statistics, alert on queries >50/request.

Fix: JOIN FETCH, @EntityGraph, @BatchSize, or DTO projections.

Issue

Slow Startup

Causes: Classpath scanning too broad, heavy eager beans, slow DB connections.

Fix: Narrow @ComponentScan basePackages, use spring.main.lazy-initialization in dev.

Performance Optimization Techniques

JVM

JVM Tuning

  • Use G1GC (default Java 17+) or ZGC for low latency
  • Set -XX:MaxRAMPercentage=75 in containers
  • Warm up with -XX:+TieredCompilation (default)
  • Profile with async-profiler, JFR
Application

Application Level

  • Cache frequently read, rarely changing data
  • Use async for I/O-bound operations
  • Virtual Threads (Java 21 + Spring 6.1) for high concurrency
  • Use reactive WebFlux for I/O-heavy services

Memory Leak Scenarios

Static collections holding object references▼
Static Maps/Lists that accumulate objects without eviction. Fix: use WeakHashMap, bounded caches (Caffeine/Guava), or scheduled cleanup.
ThreadLocal not cleared (thread pool reuse)▼
Thread pool threads are reused. If ThreadLocal set but not cleared (MDC.clear()), old data leaks to next request. Always clear in finally block.
Unclosed database/HTTP connections▼
Not closing ResultSets, Connections, or HTTP clients causes leak. Use try-with-resources. Enable hikari.leak-detection-threshold to detect unreturned connections.
Spring Security SecurityContextHolder in async threads▼
SecurityContext is ThreadLocal-based. In async threads, the context won't be propagated by default. Use DelegatingSecurityContextExecutor or set SecurityContextHolder.MODE_INHERITABLETHREADLOCAL.
Large Hibernate 1st-level cache in long transactions▼
The 1st-level cache (session) holds every loaded entity. Long batch transactions can exhaust heap. Periodically call entityManager.clear() in batch loops, or use stateless sessions for bulk ops.

Frequently Asked Interview Questions

100+ Q&A
What is @SpringBootApplication composed of?▼
It's a composite annotation combining @Configuration (class as bean source), @EnableAutoConfiguration (triggers auto-config), and @ComponentScan (scans package and sub-packages for components). You can replace it with these three individually for finer control.
How does Spring Boot detect web application type?▼
SpringApplication deduces the WebApplicationType by checking classpath: if spring-webmvc is present → SERVLET; if spring-webflux → REACTIVE; otherwise → NONE. You can override with app.setWebApplicationType(WebApplicationType.SERVLET).
What's the difference between @Component, @Service, @Repository?▼
All are specializations of @Component. @Service marks service layer (no extra behavior). @Repository additionally enables persistence exception translation — JPA/JDBC exceptions are translated to Spring's DataAccessException hierarchy. Use the most specific annotation for clarity.
What is BeanPostProcessor?▼
An interface with postProcessBeforeInitialization and postProcessAfterInitialization hooks called for every bean. AOP proxy creation happens in postProcessAfterInitialization. Used internally by Spring for many features. Implement to wrap or replace beans transparently.
What happens if two beans of the same type exist and @Primary is not set?▼
Spring throws NoUniqueBeanDefinitionException at startup. Resolve by: marking one @Primary, using @Qualifier at injection sites, or injecting a List<T> or Map<String, T> to get all beans.
What is OSIV (Open Session In View) and why should you disable it?▼
OSIV keeps the JPA session open until the HTTP response is sent, allowing lazy loading in view templates. It's enabled by default in Spring Boot. Problems: holds DB connections through view rendering, causes hidden N+1 in view layer, unclear transaction boundaries. Always set spring.jpa.open-in-view=false in production and load all needed data in the service layer.
How does @Conditional work internally?▼
During context refresh, Spring evaluates all @Conditional annotations before registering bean definitions. Each condition implements the Condition interface with a matches() method that receives the ConditionContext (classpath, environment, BeanDefinitionRegistry). If any condition returns false, the bean definition is skipped entirely.
What is the difference between save() and saveAndFlush()?▼
save() persists entity to the session (1st level cache) but may not flush to DB immediately — happens at transaction commit or when Hibernate decides. saveAndFlush() forces an immediate SQL flush. Use saveAndFlush() when you need the DB state visible immediately (e.g., before a native query in the same transaction).
What is the difference between @Entity merge() and persist()?▼
persist() makes a transient entity managed — must be called on a new entity. Throws exception if entity already has an ID in the DB. merge() copies state from detached entity to a managed one, or inserts if not found. JPA's save() in Spring Data JPA uses persist() for new entities (no ID) and merge() for detached ones.
What is the @Transactional propagation REQUIRED vs REQUIRES_NEW?▼
REQUIRED (default): joins existing transaction or creates new one. Both methods participate in the same transaction — if inner rolls back, outer rolls back too. REQUIRES_NEW: always suspends outer transaction, creates fresh one. Inner transaction commits/rolls back independently. Use for audit logging that must always commit regardless of outer outcome.
How does Hibernate 2nd-level cache work?▼
1st-level cache is per session. 2nd-level cache (e.g., Ehcache, Infinispan) is shared across sessions and can dramatically reduce DB reads for frequently read, rarely modified data. Enable per-entity: @Cache(usage = CacheConcurrencyStrategy.READ_WRITE). Requires spring.jpa.properties.hibernate.cache.use_second_level_cache=true.
What is the difference between @SequenceGenerator and @TableGenerator for IDs?▼
@SequenceGenerator uses DB sequences (PostgreSQL, Oracle) — efficient, minimal contention, batched with allocationSize. @TableGenerator uses a special DB table to simulate sequences — works on all DBs but has locking overhead. For MySQL without sequence support, use @GeneratedValue(strategy=IDENTITY) to use AUTO_INCREMENT.
What's the difference between authentication and authorization?▼
Authentication: verifying WHO you are (valid JWT token, correct password). Authorization: verifying WHAT you can do (do you have ADMIN role, do you own this resource). Spring Security's filter chain authenticates first, then the AccessDecisionManager authorizes.
What are the risks of storing JWT in localStorage vs httpOnly cookie?▼
localStorage is vulnerable to XSS — any injected script can steal the token. httpOnly cookies cannot be accessed by JavaScript — protected from XSS. However, httpOnly cookies are vulnerable to CSRF attacks (mitigated by SameSite=Strict/Lax attribute or CSRF token). For SPAs, httpOnly cookies with SameSite=Strict is recommended over localStorage.
How do you invalidate a JWT token before expiry?▼
JWTs are stateless by design — the server can't invalidate them. Solutions: (1) Short expiry (15 min) + refresh tokens. (2) Token blocklist in Redis — on logout, store token JTI in Redis with TTL = token remaining lifetime. Check on every request. (3) Token versioning — store user's token version in DB, increment on logout, validate in JWT claim.
What is CORS and how to configure it in Spring Boot?▼
CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks requests from different origins. Configure in Spring Security's filterChain with http.cors(c -> c.configurationSource(corsConfigurationSource())) or globally via @CrossOrigin on controllers. Never use allowedOrigins("*") with allowCredentials(true) — they are mutually exclusive.
What causes Spring Boot to start slowly?▼
Common causes: (1) Component scanning too broad — use specific basePackages. (2) Too many eager singleton beans. (3) Slow DB connection at startup. (4) Spring Cloud config server timeout. (5) Heavy @PostConstruct initialization. Use SpringApplication.addInitializers() and startup events to profile. Spring Boot 3.x has startup actuator endpoint.
What is the difference between WebMVC (blocking) and WebFlux (reactive)?▼
WebMVC uses Servlet API — one thread per request, blocked during I/O (DB, HTTP calls). Scales with thread pool size. WebFlux uses Netty/reactive streams — non-blocking I/O, small fixed thread pool handles millions of concurrent connections. WebFlux excels when you have many concurrent I/O-bound operations. WebMVC is simpler and still perfectly fine for most enterprise apps.
How does @Cacheable interact with @Transactional?▼
@Cacheable is applied before entering the method, while @Transactional wraps the method execution. Both work via AOP proxy. Important: cache is populated even if the transaction later rolls back — this can cause stale cache data. Use @CacheEvict carefully and consider transaction-aware cache implementations.
What is the advantage of Virtual Threads in Java 21 for Spring Boot?▼
Virtual threads (Project Loom) are lightweight JVM-managed threads — millions can exist simultaneously. When a virtual thread blocks on I/O (DB query, HTTP call), the underlying platform thread is released (mounted on another task). For Spring Boot: enables traditional servlet model to handle much higher concurrency without reactive code. Enable with spring.threads.virtual.enabled=true in Boot 3.2+.
How do you handle distributed transactions in microservices?▼
2PC (Two-Phase Commit) is generally avoided in microservices — it's blocking and couples services. Instead: (1) Saga Pattern — sequence of local transactions with compensating transactions for rollback (choreography or orchestration). (2) Outbox Pattern — write event to outbox table in same DB transaction, separate process publishes to Kafka. (3) Eventual consistency — accept temporary inconsistency, reconcile asynchronously.
What is the Outbox Pattern?▼
Solves the dual-write problem (save to DB AND publish to Kafka atomically). Instead, write the event to an "outbox" table in the same DB transaction as your business data. A separate poller (Debezium CDC, or scheduled job) reads the outbox and publishes to Kafka, then marks as processed. Guarantees at-least-once delivery without distributed transactions.
What is service mesh and how does it relate to Spring Cloud?▼
Service mesh (Istio, Linkerd) moves cross-cutting concerns (mTLS, retries, circuit breaking, tracing) to the infrastructure sidecar proxy layer, making them language/framework agnostic. Spring Cloud implements these in-application. In Kubernetes-first environments, service mesh + Micrometer Tracing is often preferred over Spring Cloud Netflix stack. Both approaches are valid — choice depends on platform maturity.
How do you implement idempotent APIs?▼
Accept an Idempotency-Key header from the client (UUID). Before processing, check if this key exists in Redis. If found, return the cached response. If not, process the request, store the result in Redis with TTL (e.g., 24 hours) keyed by the idempotency key. Idempotent POST operations are safe to retry — critical for payment APIs.
When would you NOT use Spring Boot / microservices?▼
Microservices add operational complexity: multiple deployments, distributed tracing, eventual consistency challenges, service discovery, increased latency. Don't use if: small team (<5 devs), simple domain, startup phase, tight deployment coupling needed. Start with a well-structured monolith ("modular monolith") and extract services only when you have clear team/scaling boundaries.
How do you design an API for pagination that supports large datasets?▼
Offset pagination (?page=5&size=20) degrades at large offsets (DB must scan and skip). For large datasets use cursor-based pagination: return nextCursor (encoded last-seen ID or timestamp) in response, client passes ?after=cursor in next request. DB query becomes WHERE id > :cursor ORDER BY id LIMIT 20 — uses index efficiently at any scale.
What are the SOLID principles and how do they apply to Spring?▼
Single Responsibility: one service per domain concept. Open/Closed: use interfaces + @Bean, extend via new implementations not modification. Liskov: ensure subtypes honor contracts — important for repository interfaces. Interface Segregation: small focused interfaces (UserReader, UserWriter vs UserService). Dependency Inversion: inject interfaces not concretions — Spring DI enforces this naturally via constructor injection.
How do you handle breaking API changes without downtime?▼
Use versioned APIs (/v1/, /v2/). Deploy v2 alongside v1. Migrate consumers gradually. Keep v1 alive during migration period. Use feature flags to route traffic. For DB changes: expand-contract pattern — add new column (nullable), deploy code supporting both old/new, migrate data, deploy code dropping old column, drop column. Never drop/rename columns in a single deploy.
