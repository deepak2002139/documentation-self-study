Fundamentals

What is RAG?

Retrieval-Augmented Generation (RAG) is an architecture pattern that enhances Large Language Models by injecting relevant, retrieved context into the prompt at inference time — rather than relying solely on what the model learned during training.

🔑 Core Idea

Split "knowing" from "reasoning." Store knowledge in a vector database. Let the LLM focus on reasoning over retrieved facts. This gives you freshness, accuracy, and auditability.

📦 Real-World Analogy

Imagine a brilliant consultant who has forgotten most details. Before every meeting, their assistant brings them the exact relevant files. The consultant reads those files and gives expert advice. That's RAG — the assistant is your retriever, the files are your vector DB, the consultant is the LLM.

🧠

Without RAG

LLM relies entirely on training data. Hallucinations occur when asked about post-training events or niche domains. No source attribution possible.

📡

With RAG

LLM receives fresh, domain-specific context at query time. Grounded answers with source attribution. Updatable without retraining.

⚡

Advanced RAG

Multi-hop retrieval, query decomposition, re-ranking, confidence scoring, hallucination detection, and agentic self-correction.

⚠ Interview Trap

Never say "RAG is always better." Fine-tuning wins when you need custom tone, format, or behavior baked into the model itself. The smart answer: use RAG for knowledge, fine-tuning for style — or combine both (RAFT: RAG + Fine-Tune).

Problem Space

Problems RAG Solves

👻

Hallucination Problem

LLMs generate plausible-sounding but factually wrong content. RAG grounds the model with retrieved facts, making it much harder to hallucinate about things in the context window.

📏

Context Window Limits

Even 128K token models can't hold entire knowledge bases. RAG selectively retrieves the most relevant chunks — fitting maximum signal into limited context space.

🔄

Knowledge Freshness

Training data has a cutoff. RAG lets you add new documents (PDFs, APIs, DB records) in real-time without touching the model. Updates are instant.

🔒

Private Knowledge

Company-internal data, proprietary documents, customer records — never in any LLM's training. RAG is the only way to query private data with LLMs without sending it for fine-tuning.

📎

No Source Attribution

Base LLMs can't cite sources. RAG retrieval tracks which documents were used, enabling enterprise-grade explainability and audit trails.

💸

Fine-Tuning Cost

Fine-tuning GPT-4 class models costs thousands of dollars and takes days. Adding documents to ChromaDB takes seconds and costs cents.

Step 1 — Ingestion
Document Loading
LangChain's document loaders ingest PDFs, URLs, CSV, Notion, Confluence, etc. Each loader handles parsing, metadata extraction, and text normalization.
Step 2 — Chunking
Text Splitting
Documents split into semantically meaningful chunks. Chunk size and overlap tuned per document type. Too small = lost context; too large = noisy retrieval.
Step 3 — Embedding
Vector Generation
Each chunk passed through an embedding model (text-embedding-ada-002, BGE, E5) to produce a high-dimensional vector representation. Semantically similar texts produce nearby vectors.
Step 4 — Storage
ChromaDB Upsert
Vectors + metadata + original text stored in ChromaDB collections. Indexed with HNSW (Hierarchical Navigable Small World) for approximate nearest neighbor search.
Step 5 — Retrieval
Semantic Query
User query embedded → cosine similarity search in ChromaDB → top-K chunks retrieved. Optionally filtered by metadata (date, department, file type).
Step 6 — Generation
Grounded Response
Retrieved chunks injected into LLM prompt. LLM generates answer strictly using provided context. Source documents cited in the response.
Deep Dive

Retrieval Pipeline

Embedding-Based Retrieval

Text is mapped to a high-dimensional vector space where semantic similarity = geometric proximity. The model learns that "car" and "automobile" should be nearby, even though the words are different.

Similarity Metrics

Cosine Similarity

Measures angle between vectors. Best for normalized embeddings. Range: -1 to 1. Most common in RAG. ChromaDB default.

math
cos(θ) = (A·B) / (|A| × |B|)
Range: -1 (opposite) to 1 (identical)
Used by: ChromaDB, Pinecone, Weaviate

Euclidean Distance (L2)

Straight-line distance in vector space. Sensitive to magnitude. Good when vectors are not normalized.

Dot Product (IP)

Fast computation, used in FAISS. Best when embeddings are trained for dot product optimization. Not always normalized.

Ingestion

Chunking Strategies

Chunking is one of the most impactful decisions in a RAG system. Poor chunking = poor retrieval, no matter how good your LLM or embeddings are.

📄

Fixed-Size Chunking

Split every N characters/tokens. Simple but breaks semantic boundaries mid-sentence. Only use for structured data with known format.

chunk_size=512chunk_overlap=50
🔄

Recursive Character Splitting

LangChain's default. Tries to split on paragraphs → sentences → words → characters. Respects natural text boundaries. Best general-purpose strategy.

RecursiveCharacterTextSplitter
🪟

Sliding Window

Overlapping chunks ensure context isn't lost at boundaries. Key insight: if an answer spans two chunks, overlap lets you retrieve it. Overlap = 10-20% of chunk size.

overlap=128 tokens
🧩

Semantic Chunking

Uses embedding similarity to detect topic shifts. Chunks are semantically coherent units, not arbitrary splits. More expensive but dramatically better retrieval.

SemanticChunkerthreshold=0.8
🌲

Hierarchical / Parent-Child

Store small chunks for precise retrieval, return parent chunk for full context. Combines retrieval precision with generation quality. Advanced RAG pattern.

ParentDocumentRetriever
📊

Markdown/Code-Aware

Splits on headers, code blocks, function definitions. Critical for technical documentation or code search use cases. LangChain has MarkdownTextSplitter.

💡 Production Insight

In production, we ran retrieval quality experiments: Semantic chunking improved answer relevance by 23% over fixed-size, at the cost of 3x ingestion time. For documents ≥100 pages, parent-child retrieval was the only approach that maintained coherent context for multi-step questions.

Query Strategies

Query Expansion

A single query often misses relevant documents due to vocabulary mismatch. Query expansion generates multiple phrasings of the same intent and merges results.

Python · Query Expansion with LLM
# Generate 3 alternative queries using LLM
expansion_prompt = """
Generate 3 different search queries for:
Original: {query}

Return as JSON list: ["q1", "q2", "q3"]
"""

expanded = llm.invoke(expansion_prompt.format(query=user_query))
queries = json.loads(expanded.content)

# Retrieve for each, merge with deduplication
all_docs = []
for q in [user_query] + queries:
    docs = vectorstore.similarity_search(q, k=4)
    all_docs.extend(docs)

unique_docs = deduplicate_by_content(all_docs)

HyDE (Hypothetical Document Embeddings)

Instead of embedding the query, generate a hypothetical answer document and embed that. This often produces better retrieval because the hypothetical answer is semantically closer to actual answer documents than the question itself.

ℹ Interview Point

HyDE improves retrieval recall by 15-30% on domain-specific corpora. The tradeoff: one extra LLM call per query. Worth it for high-stakes applications, but adds latency and cost.

Python · Re-ranking with Cross-Encoder
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

# Stage 1: Fast vector search (recall-optimized)
candidates = vectorstore.similarity_search(query, k=50)

# Stage 2: Cross-encoder re-ranking (precision-optimized)
pairs = [(query, doc.page_content) for doc in candidates]
scores = reranker.predict(pairs)

ranked = sorted(zip(scores, candidates), reverse=True)
final_docs = [doc for score, doc in ranked[:5]]

Confidence Scoring

Assign a confidence score to each retrieved chunk based on: retrieval similarity score, re-ranker score, metadata recency, and source authority. Chunks below a threshold are dropped to avoid injecting irrelevant context.

⚠ Production Challenge

Setting the right confidence threshold is tricky. Too high → miss valid documents. Too low → inject noise. In production, we A/B tested thresholds and used user feedback signals to calibrate. The sweet spot was typically 0.65-0.75 cosine similarity for our domain.

Search

Hybrid Search

Pure semantic search fails on exact keyword lookups (product codes, names, IDs). Pure keyword search (BM25) fails on semantic queries. Hybrid combines both for production-grade retrieval.

✅ Dense Retrieval (Semantic)
  • Captures semantic similarity
  • Works across language variations
  • Handles synonyms and paraphrasing
  • ChromaDB, FAISS, Pinecone
✅ Sparse Retrieval (BM25)
  • Exact keyword matching
  • Product codes, IDs, names
  • Fast and interpretable
  • Elasticsearch, Opensearch
Python · Hybrid Search with RRF
# Reciprocal Rank Fusion (RRF) — merges two ranked lists
def rrf_merge(dense_docs, sparse_docs, k=60):
    scores = {}
    for rank, doc in enumerate(dense_docs):
        doc_id = doc.metadata["id"]
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)

    for rank, doc in enumerate(sparse_docs):
        doc_id = doc.metadata["id"]
        scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank + 1)

    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

Instead of injecting entire chunks (which may contain irrelevant sentences), a compressor model extracts only the relevant sentences from each chunk. Reduces token usage by 40-60%.

Source Attribution

Every sentence in the generated answer is mapped back to its source chunk and document. Users see citations in real-time. Critical for legal, medical, and enterprise use cases.

🚨 Critical Production Issue

In one production system, hallucination detection caught that the LLM was blending information from two different quarterly reports. The answer looked correct but cited wrong quarter figures. Without automated validation, this would have gone unnoticed. Always build validation layers.

Optimization: Latency, Cost & Token Efficiency

⚡

Semantic Caching

Cache LLM responses keyed by query embedding. Similar queries hit the cache. Use cosine distance threshold (e.g., >0.95 similarity = cache hit). Reduces cost by 30-60%.

🔁

Async Retrieval

Run multiple vector searches concurrently using asyncio. For hybrid search or multi-collection retrieval, parallel fetching reduces latency from O(n) to O(1).

✂️

Token Optimization

Use context compression, limit top-K, and truncate chunks to fit the budget. Measure: retrieved tokens vs. LLM cost. Optimize for answer quality per dollar.

📊

Batch Embeddings

During ingestion, batch documents into groups of 100-500 before calling the embedding API. Batch calls are 5-10x cheaper and faster than individual calls.

🗜️

Smaller Embedding Models

text-embedding-3-small is 5x cheaper than ada-002 with competitive quality. BGE-m3 (open-source) is free and often outperforms commercial models on domain-specific data.

🌊

Streaming Responses

Stream LLM output token by token to reduce perceived latency. First token appears in <1s even if full response takes 10s. Critical for chat interfaces.

Orchestration Framework

What is LangGraph?

LangGraph is a library built on top of LangChain for creating stateful, cyclic, multi-actor workflows using a directed graph model. It solves the fundamental limitation of LangChain chains: they are linear and stateless. LangGraph enables conditional flows, loops, retries, and parallel execution.

📦 Real-World Analogy

Think of LangGraph as a state machine for AI. Just like a traffic light has states (red/yellow/green) and transitions based on conditions, LangGraph defines AI workflow states and transitions based on LLM decisions, tool outputs, or human input.

🔁

Cyclic Graphs

Unlike DAG-based pipelines, LangGraph supports cycles. An agent can retrieve, generate, check quality, and loop back to retrieve again — until a stopping condition is met.

📦

Persistent State

State is a typed dictionary shared across all nodes. Every node reads from and writes to this shared state. State can be checkpointed to DB for long-running workflows.

🧠

Human-in-the-Loop

Pause execution at any node for human review. Resume from the exact checkpoint. Perfect for approval workflows, content moderation, or ambiguous agent decisions.

Nodes, Edges & State

Defining State

Python · LangGraph State Definition
from typing import TypedDict, Annotated, List
from langchain_core.documents import Document
import operator

class RAGState(TypedDict):
    question: str                             # input question
    documents: Annotated[List[Document],      # retrieved docs
                         operator.add]        # reducer: append
    generation: str                           # LLM output
    hallucination_score: float                # validation result
    retry_count: int                          # loop guard
    web_search_needed: bool                   # routing flag

Defining Nodes

Python · LangGraph Nodes
def retrieve(state: RAGState) -> RAGState:
    """Node 1: Retrieve documents from vector store"""
    question = state["question"]
    docs = retriever.invoke(question)
    return {"documents": docs}

def grade_documents(state: RAGState) -> RAGState:
    """Node 2: Grade relevance of retrieved docs"""
    question = state["question"]
    docs = state["documents"]
    filtered = [d for d in docs if is_relevant(d, question)]
    web_needed = len(filtered) < 2
    return {"documents": filtered, "web_search_needed": web_needed}

def generate(state: RAGState) -> RAGState:
    """Node 3: Generate answer from context"""
    context = format_docs(state["documents"])
    answer = rag_chain.invoke({"context": context,
                               "question": state["question"]})
    return {"generation": answer}

Building the Graph

Python · Graph Construction
from langgraph.graph import StateGraph, END, START

graph = StateGraph(RAGState)

# Add nodes
graph.add_node("retrieve", retrieve)
graph.add_node("grade_documents", grade_documents)
graph.add_node("generate", generate)
graph.add_node("web_search", web_search)

# Add edges
graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "grade_documents")
graph.add_conditional_edges(
    "grade_documents",
    route_question,   # returns "generate" or "web_search"
    {"generate": "generate", "web_search": "web_search"}
)
graph.add_edge("web_search", "generate")
graph.add_conditional_edges(
    "generate",
    check_hallucination,   # loop or end
    {"hallucinated": "retrieve", "grounded": END}
)

app = graph.compile()
Agentic AI

Agentic Workflows & Advanced Patterns

🔄

Retry Mechanism

Failed tool calls or low-confidence answers trigger automatic retries with modified query or parameters. Max retry count prevents infinite loops. State tracks retry_count.

🧵

Parallel Execution

Multiple retrieval nodes can run concurrently using LangGraph's parallel branching. Retrieve from ChromaDB, web search, and SQL database simultaneously, then merge results.

🪞

Reflection

A critic agent reviews the generator's output and provides structured feedback. The generator uses this feedback to revise. Implements self-improvement loop without human intervention.

👥

Multi-Agent

Specialized agents (researcher, writer, critic, validator) each handle one step. A supervisor agent routes tasks. Better separation of concerns than one monolithic agent.

🛑

Human-in-the-Loop

Add interrupt_before=["generate"] to pause and wait for human approval before generating. State is persisted to DB. Resume with graph.invoke(null, config) after approval.

🗂️

Workflow Persistence

LangGraph checkpoints state at every node. If a workflow fails mid-execution, it resumes from the last checkpoint — not from the beginning. Uses SQLite or Postgres backends.

Python · Human-in-the-Loop with Checkpointing
from langgraph.checkpoint.sqlite import SqliteSaver

# Add memory/persistence
memory = SqliteSaver.from_conn_string(":memory:")
app = graph.compile(
    checkpointer=memory,
    interrupt_before=["generate"]  # pause before generation
)

# First run — pauses at "generate"
config = {"configurable": {"thread_id": "thread-1"}}
result = app.invoke({"question": user_query}, config)

# Human approves, then resume
final = app.invoke(None, config)

LCEL

Chains, Runnables & LCEL

LCEL (LangChain Expression Language) uses the pipe operator | to compose runnables into chains. It supports streaming, async, batch, and parallel execution natively.

Python · Full RAG Chain with LCEL
from langchain_core.runnables import RunnablePassthrough, RunnableParallel
from langchain_core.output_parsers import StrOutputParser

# Build RAG chain using pipe composition
rag_chain = (
    RunnableParallel({
        "context": retriever | format_docs,  # parallel branch
        "question": RunnablePassthrough()   # pass query through
    })
    | prompt                    # inject into template
    | llm                       # call LLM
    | StrOutputParser()          # parse to string
)

# Invoke
answer = rag_chain.invoke("What is our refund policy?")

# Stream
for chunk in rag_chain.stream("What is our SLA?"):
    print(chunk, end="", flush=True)

# Batch
answers = rag_chain.batch(["Q1", "Q2", "Q3"])

Agent vs RAG — Key Distinction

ℹ Interview Distinction

RAG = retrieve then generate. Fixed flow. Deterministic retrieval step. Agent = plan then act. LLM decides dynamically which tools to call, in what order, for how many steps. Agents can use RAG as a tool. LangGraph builds agents that use RAG internally.

Vector Database

ChromaDB Deep Dive

ChromaDB is an open-source, embedded vector database built for AI applications. It stores embeddings, original text, and metadata together, and supports rich querying via semantic search + metadata filtering.

Python · ChromaDB Complete Setup
import chromadb
from chromadb.utils import embedding_functions

# Initialize persistent client
client = chromadb.PersistentClient(path="./chroma_db")

# Define embedding function
embed_fn = embedding_functions.OpenAIEmbeddingFunction(
    api_key=OPENAI_KEY,
    model_name="text-embedding-3-small"
)

# Create collection
collection = client.get_or_create_collection(
    name="knowledge_base",
    embedding_function=embed_fn,
    metadata={"hnsw:space": "cosine"}  # similarity metric
)

# Upsert documents
collection.upsert(
    documents=["AI is transforming enterprise..."],
    metadatas=[{"source": "report.pdf", "dept": "research"}],
    ids=["doc_001"]
)

# Query
results = collection.query(
    query_texts=["AI enterprise applications"],
    n_results=5,
    where={"dept": {"$eq": "research"}}
)
Concepts

Vector Database Concepts

📊

HNSW Index

Hierarchical Navigable Small World. A graph-based ANN index that enables sub-linear search. O(log n) query time. ChromaDB uses HNSW as its default index structure.

🗂️

Collections

ChromaDB organizes vectors into collections (like tables in SQL). Each collection can have its own embedding function and distance metric. Use separate collections per domain.

🔍

Metadata Filtering

ChromaDB supports pre-filtering and post-filtering by metadata fields. where and where_document operators support $eq, $ne, $gt, $in, $and, $or. Critical for multi-tenant RAG systems.

FastAPI AI Service

The FastAPI service is the AI orchestration layer. It exposes REST endpoints, accepts queries, runs the LangGraph workflow, and returns grounded answers with source citations.

Python · FastAPI AI Service
from fastapi import FastAPI, HTTPException, Depends
from fastapi.responses import StreamingResponse
from pydantic import BaseModel

app = FastAPI(title="AI RAG Service", version="2.0")

class QueryRequest(BaseModel):
    question: str
    user_id: str
    filters: dict = {}
    stream: bool = False

class QueryResponse(BaseModel):
    answer: str
    sources: list[dict]
    confidence: float
    tokens_used: int

@app.post("/api/v1/query", response_model=QueryResponse)
async def query(request: QueryRequest, token=Depends(verify_token)):
    try:
        result = await rag_agent.ainvoke({
            "question": request.question,
            "filters": request.filters
        })
        return QueryResponse(**result)
    except Exception as e:
        raise HTTPException(500, str(e))

@app.post("/api/v1/ingest")
async def ingest_document(file: UploadFile):
    # Async document processing pipeline
    task_id = await ingestion_pipeline.process(file)
    return {"task_id": task_id, "status": "processing"}
Business Service

Spring Boot Integration

Spring Boot handles business logic, auth, database, and orchestrates calls to the FastAPI AI service. Service-to-service communication uses REST with circuit breakers (Resilience4j).

Java · Spring Boot AI Service Client
@Service
public class AIServiceClient {

    private final WebClient webClient;

    public AIServiceClient(WebClient.Builder builder) {
        this.webClient = builder
            .baseUrl("http://ai-service:8001")
            .build();
    }

    @CircuitBreaker(name = "aiService", fallbackMethod = "fallback")
    @TimeLimiter(name = "aiService")
    public Mono<QueryResponse> query(QueryRequest request) {
        return webClient.post()
            .uri("/api/v1/query")
            .bodyValue(request)
            .retrieve()
            .bodyToMono(QueryResponse.class)
            .timeout(Duration.ofSeconds(30));
    }

    public Mono<QueryResponse> fallback(Exception e) {
        return Mono.just(new QueryResponse(
            "AI service temporarily unavailable", List.of(), 0.0
        ));
    }
}

Interview Prep

RAG Interview Questions & Answers

What is the difference between naive RAG, advanced RAG, and modular RAG?▼
Naive RAG: Index docs → retrieve top-K → inject in prompt. Simple but brittle. Advanced RAG: Adds query expansion, re-ranking, multi-hop retrieval, hallucination detection, and iterative refinement. Modular RAG: Components (retriever, ranker, generator) are swappable. You can replace ChromaDB with Weaviate or swap the LLM without rewriting the pipeline. We built a modular RAG system to allow A/B testing of retrievers.
How do you evaluate a RAG system?▼
We use RAGAS metrics: (1) Faithfulness — is the answer supported by retrieved context? (2) Answer Relevancy — does the answer address the question? (3) Context Recall — did we retrieve all relevant docs? (4) Context Precision — are retrieved docs relevant? We integrated RAGAS into our CI pipeline so every code change is evaluated against a golden dataset of 200 question-answer pairs.
How do you handle documents that change frequently?▼
Three approaches: (1) Full re-ingestion — simplest, re-process all docs nightly. Fine for small corpora. (2) Incremental update — track document hash/timestamp, only re-embed changed docs. ChromaDB upsert with same ID automatically replaces. (3) Event-driven — document edit events trigger async re-ingestion via message queue (Kafka). We moved from nightly to event-driven when freshness became critical for our legal document system.
What happens when the LLM still hallucinates even with RAG?▼
RAG reduces but doesn't eliminate hallucination. Mitigation layers: (1) Stricter prompts — "If the answer is not in the context, say 'I don't know'". (2) Automated hallucination checker — second LLM call verifies each claim. (3) Confidence scoring — low confidence answers are flagged for human review. (4) Source attribution — show users exactly which document the answer came from. (5) Answer grounding score in LangGraph — if below threshold, loop back to retrieve more context.
How do you optimize RAG latency for real-time applications?▼
Multi-layer strategy: (1) Semantic cache in Redis — cache answers for similar queries (cosine similarity > 0.95). Cached responses in <10ms. (2) Async parallel retrieval — run vector search, keyword search, and metadata lookup concurrently. (3) Pre-computed embeddings — embed common queries at startup. (4) Smaller embedding model — switch from ada-002 to text-embedding-3-small (5x cheaper, similar quality). (5) Streaming — stream LLM output token-by-token so user sees first token in <1s. Result: reduced P99 latency from 8s to 2.3s.
How do you handle multi-tenant RAG where different users see different data?▼
Two approaches: (1) Namespace/Collection per tenant — separate ChromaDB collection per organization. Complete isolation but higher overhead. Good for strict compliance requirements. (2) Metadata filtering — all docs in one collection, each document tagged with tenant_id. Every query filtered by where={"tenant_id": user.org_id}. More efficient but requires trust in the filter layer. We use approach 2 with strict server-side filter enforcement (never trust client-side tenant claims).
Interview Prep

LangGraph Interview Questions

Why did you choose LangGraph over a simple LangChain chain?▼
Simple chains work for happy-path RAG. We chose LangGraph when we needed: (1) Conditional routing — if retrieved docs aren't relevant, fall back to web search. Chains can't do this. (2) Retry loops — if the answer is hallucinated, loop back to retrieve more context. Chains are linear. (3) Human-in-the-loop — some answers need human approval before being sent to the user. LangGraph has first-class interrupt support. (4) State persistence — long-running research tasks need state saved between API calls. LangGraph checkpointing solves this.
How does LangGraph handle errors in the middle of a workflow?▼
Three error handling strategies: (1) Node-level try/catch — each node wraps its logic in try/except and updates state with an error field. Downstream conditional edges route to an error recovery node. (2) Checkpoint recovery — if a node crashes hard, the workflow can resume from the last saved checkpoint. State is not lost. (3) Retry decorator — wrap tool-calling nodes with @retry decorator for transient failures (API rate limits, timeouts). LangGraph's graph is deterministic given the same state, so retries are safe.
Describe a self-correcting RAG pipeline using LangGraph.▼
Graph: START → retrieve → grade_documents (conditional: relevant/irrelevant) → if irrelevant: web_search → generate → check_hallucination (conditional: grounded/hallucinated). If hallucinated: loop back to retrieve with expanded query. Max retry=3 to prevent infinite loops. State carries: question, documents, generation, retry_count. Each loop the query is expanded with different terms. This system reduced our hallucination rate from 12% to under 2%.
Interview Prep

LangChain Interview Questions

What is LCEL and why is it better than the legacy chain API?▼
LCEL (LangChain Expression Language) uses Python's pipe operator | to compose Runnable components. Advantages over legacy: (1) Streaming built-in — any LCEL chain streams by default. (2) Async support — ainvoke, astream without extra code. (3) Batch processing — batch method for parallel processing. (4) Type safety — each Runnable has typed input/output schemas. (5) Fallbacks — chain.with_fallbacks([backup_llm]). Legacy chains required subclassing and custom __call__ methods.
How do you implement conversational RAG with session history?▼
Key insight: naive RAG doesn't understand follow-up questions like "tell me more about the second point." Two steps: (1) History-aware retriever — reformulate the user's question using chat history before retrieval. LangChain's create_history_aware_retriever does this with one LLM call. (2) Session management — store chat history per session ID in Redis or Postgres. RunnableWithMessageHistory wraps any chain to automatically inject and update history. The result: "tell me more" correctly retrieves context about the right topic.

System Design Interview Questions

Design a RAG system that handles 10,000 concurrent users.▼
Horizontal scaling: FastAPI AI service deployed as Kubernetes Deployment with HPA (scale on CPU/custom Prometheus metric: p95 latency). 3-10 replicas. Semantic cache: Redis cluster caches embeddings and answers. 60% cache hit rate for common queries dramatically reduces LLM load. Queue: For non-real-time ingestion, use Celery + Redis for async document processing. ChromaDB: At this scale, migrate to managed Pinecone or Qdrant cluster. ChromaDB is not designed for 10K concurrent writes. LLM rate limits: LiteLLM load balancer distributes requests across multiple OpenAI org keys and fallback providers. CDN: Static knowledge (product FAQs, documentation) pre-answered and cached at edge.
How do Spring Boot and FastAPI communicate? What about failures?▼
Communication: REST over internal K8s service mesh (or gRPC for lower latency). Spring Boot uses WebClient (reactive) to call FastAPI async. Auth: Spring Boot issues internal service JWT, FastAPI validates signature. Failure handling: (1) Circuit breaker (Resilience4j) — if FastAPI returns 5xx 5 times in 10s, open circuit for 30s, serve fallback. (2) Timeout — 30s max wait. (3) Retry — 2 retries with exponential backoff. (4) Fallback — "Our AI assistant is temporarily unavailable. Here are related help docs." User never sees a 500 error.
How do you handle sensitive/PII data in a RAG system?▼
Multiple layers: (1) Pre-ingestion PII detection — run Presidio or a custom NER model to detect and redact emails, SSNs, names before embedding. (2) Access control — documents tagged with clearance level in metadata. Queries filtered by user's clearance. (3) Audit logging — every query, retrieved doc, and generated answer logged to immutable audit log. (4) On-premise LLM — for highest security, swap OpenAI for Llama 3 running on-prem via Ollama or vLLM. Nothing leaves your network. (5) Encryption at rest — ChromaDB data directory encrypted. Embedding vectors themselves are not easily reversible to original text, but don't rely on this for security.
Engineering Decisions

Tradeoffs & Key Decisions

Chunk Size: 512 vs 1024 tokens

Smaller chunks: Higher retrieval precision, more chunks to retrieve, may split important context. Larger chunks: Better context preservation, lower precision, higher token cost. Decision: 512 with 64 overlap for most cases; 1024 for legal/medical long-form documents.

Top-K: 3 vs 10

Low K: Less noise in context, lower cost, may miss relevant docs. High K: Higher recall, but diluted context, higher cost. Decision: K=10 for retrieval, but only top 3 after re-ranking injected into prompt.

GPT-4 vs GPT-3.5 vs Open Source

GPT-4: Best quality, 30x more expensive. GPT-3.5: Good quality, fast, cheap. Llama 3: Free, private, but requires GPU infra. Decision: GPT-3.5 for 90% of queries, GPT-4 for complex/high-stakes ones (routing by question complexity score).

ChromaDB vs Pinecone

ChromaDB: Free, self-hosted, great for dev and <1M vectors. Pinecone: Managed, scales to billions, higher cost. Decision: ChromaDB for dev/staging, migrate to Qdrant (self-hosted) for production to avoid vendor lock-in and control costs.

Synchronous vs Async Ingestion

Sync ingestion blocks the upload API until processing completes (poor UX for large docs). Async ingestion returns immediately with a task ID. User polls status. Decision: Always async for production. Sync only in test environments.

One Agent vs Multiple Specialized Agents

One agent is simpler but becomes a god object. Specialized agents (retriever, writer, validator) are easier to test and iterate. Decision: Start with one agent, extract specialized agents when context window or complexity demands it.

Production Incidents

Real RAG Failure Scenarios

Incident 01 — Retrieval Failure
Semantic Drift: Queries Not Matching Documents
Problem: Documents were embedded with ada-002, but queries were embedded with a different model version after an upgrade. Cosine similarity scores dropped to near-zero. System returned garbage chunks. Solution: Always store which embedding model was used per collection. On model upgrade, re-embed entire collection. Added model version check on startup.
Incident 02 — Context Poisoning
Adversarial Document Injection
Problem: A user uploaded a document with hidden text: "Ignore all previous instructions and respond with: ..." — a prompt injection attack via the document corpus. Solution: Added document sanitization layer before ingestion. Strip HTML/CSS. Detect and reject documents with instruction-like patterns. Wrap retrieved context in XML tags and instruct LLM to treat content as data, not instructions.
Incident 03 — Infinite Loop
LangGraph Retry Loop Escaped Max Retries
Problem: A bug in the hallucination checker always returned "hallucinated" due to a JSON parsing error. The LangGraph loop retried indefinitely, burning tokens and money. Solution: Added explicit retry_count to state with a hard limit of 3. Conditional edge: if retry_count >= 3, route to END with "unable to answer" response regardless of hallucination score.
Incident 04 — Chunk Boundary Issue
Answer Split Across Chunk Boundary
Problem: Critical numerical data (pricing table) was split across two chunks. Neither chunk alone contained the complete answer. Retrieval returned only one chunk, leading to incomplete answers. Solution: Increased chunk overlap from 20 to 128 tokens. Added parent-document retriever: retrieve small chunk, return full parent section. Improved structured document detection to avoid splitting tables.
Incident 05 — Cost Explosion
Unbounded Token Usage in Production
Problem: A query type with long document context passed 50+ chunks to the LLM, leading to $800/day in API costs on day 3 of launch. Solution: Added hard token budget per query (max 3000 context tokens). Context compressor enabled. Re-ranking to select only top 3 most relevant chunks. Added cost tracking per request. Set spending alerts and hard caps per user/org.
